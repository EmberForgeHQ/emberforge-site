Why Nexus exists

ARK is the foundation. Connections are the product.

Nexus started with a simple problem: reliable cross-chat should not require a community to hand over its entire server operation. Instead of rebuilding deep in-game administration, Nexus focuses on the infrastructure around ARK: message routing, Discord integration, monitoring, automation, safe remote actions, and the systems that help clusters stay connected.

01 / CROSS-CHAT

Connect the whole cluster.

ARK → ARK, ARK → Discord, and Discord → ARK routing with server aliases, chat groups, basic formatting, mute controls, and loop-safe event handling.

02 / OPERATIONS

Know when something actually matters.

Premium monitoring tracks agents, servers, capabilities, routes, incidents, disconnects, recoveries, and degraded states without turning every hiccup into an alarm bell.

03 / AUTOMATION

React without bypassing safety.

Premium automation follows a clear WHEN → IF → THEN model and re-checks entitlement, capability, permission, current state, and safety before acting.

04 / RCON

Remote control without raw-console roulette.

An optional RCON layer provides approved actions such as player lookups, broadcasts, saves, kicks, bans, and restart workflows without exposing unrestricted console access.

05 / INSIGHTS

Understand activity, not individuals.

Optional community-level analytics can show chat volume, busy maps, peak hours, and trends without building player dossiers or creepy engagement rankings.

06 / MANY DOORS

One brain. Multiple interfaces.

Discord and the future dashboard both talk to the same Nexus Core, so permissions, safety, monitoring, actions, and audit behavior stay consistent everywhere.

Architecture

One Nexus Core. Many ways in and out.

Nexus separates what a community bought, what a connection can currently do, and what a person is allowed to do. Discord, the dashboard, Agents, and RCON remain distinct boundaries around one authoritative Core.

Discord + DashboardPresent state, accept requests, and translate humans into Nexus actions.
API BoundaryAuthenticates requests, validates input, establishes actor context, and invokes Core.
Nexus CoreRouting, permissions, entitlements, server registry, monitoring, automation, and action dispatch.
Agent / Direct RCONConnects outward, reports capabilities, observes ARK locally, and executes only supported actions.
ARK ServersThe game remains the destination. Nexus manages the connections around it.
Security & trust

Trust identity narrowly. Authorize centrally.

Nexus is designed around explicit boundaries. Agents do not get billing authority. Discord roles do not become permissions by magic. RCON does not become a raw command tunnel. Every layer gets only the authority it needs to do its actual job.

Entitlements

What did the community buy?

Plans and add-ons determine which product features the community may use.

Capabilities

What can this connection do right now?

Agents and connectors advertise live capabilities such as chat, status, logs, RCON, or restart control.

Permissions

What may this person do?

Human authorization is evaluated centrally and stays separate from plan ownership and connection capability.

Containment

One failure should stay one failure.

A broken server, Discord outage, failed destination, or compromised Agent should not become a platform-wide incident.

Agent rule: the Agent observes locally, executes narrowly, and decides almost nothing. Nexus Core remains the brain.
Monitoring & automation

React to the real state, not the first noisy blip.

Nexus monitoring is built around connection and capability health, with sustained-failure thresholds, incident lifecycles, recovery awareness, planned downtime, and flapping protection. Automation sits above that health model and re-checks reality before it acts.

CONNECTED

Expected capabilities are healthy.

The configured connection path is available and the functions Nexus expects for that server are working.

DEGRADED

Keep using what still works.

If logs remain available but RCON drops, Nexus can continue the healthy capability instead of declaring the entire server dead.

DISCONNECTED

Isolate, recover, resume.

Disconnected destinations stop receiving new work while healthy servers and routes continue independently.
